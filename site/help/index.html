Understanding your results

Every check ends in one of three results. Pass means AsBuilt saw what you intended. Fail means it saw something different, with a screenshot. Not verified means it couldn't tell, and says why.

What “Not verified” means

AsBuilt couldn't collect enough evidence to say pass or fail. It is never counted as a pass, and it isn't a bug report either. The line under each result says why. Find that reason below.

What to do: Read the reason, fix the setup it points to, and push again. If none of these sections fit, ask a question.

A check file couldn't run

Before checking anything, AsBuilt reads each file in .asbuilt/ and refuses to run one that's broken or asks for more than it's allowed. Nothing about your app was judged. The comment says which file and why.

What to do: Paste the reason to your assistant and ask it to fix the check file. The most common one is an interactive check without approval: once you've reviewed the check, add "actionsApproved": true. Invalid JSON and a start path that isn't a page on the preview are the next most common.

The preview is protected (HTTP 401 or 403)

The preview asked for a login before showing anything, so AsBuilt saw a lock screen instead of your site. On Vercel this is usually Deployment Protection.

What to do: In Vercel, open your project's Settings → Deployment Protection and copy the Protection Bypass for Automation secret. In GitHub, add it as the repository secret VERCEL_AUTOMATION_BYPASS_SECRET, then uncomment the vercel-bypass-secret line in .github/workflows/asbuilt.yml. AsBuilt sends it only to your preview.

The page returned an error (HTTP 500, 502 and similar)

Your preview was down or crashed when AsBuilt opened it. That's a real problem worth looking at, but AsBuilt can't tell whether your feature works until the page loads.

What to do: Open the preview yourself. If it errors, check your hosting logs and fix the crash. If it loads fine now, it was a temporary outage: re-run the workflow from the Actions tab.

The page asks for a password

AsBuilt reached a sign-in form. It never types a password unless you set up a test account, so it couldn't see what's behind it.

What to do: Either check a page that doesn't need sign-in, or add sign-in to the check with a dedicated test account. Ask your assistant: “Add AsBuilt sign-in to this check.” It will tell you which two secrets to add (ASBUILT_TEST_EMAIL and ASBUILT_TEST_PASSWORD). Never use a real customer account.

Sign-in didn't work

AsBuilt tried to sign in with your test account but couldn't confirm it worked. The reason names what went wrong: a field it couldn't find, a page that didn't load, or no proof of being signed in afterwards.

What to do: Make sure the test account exists on the preview's database and has no two-step verification. Check that the field and button names in the check match what's on screen exactly, for example “Email” and “Sign in”. If a cookie banner covers the form, add its decline button as dismiss.

The check ran without JavaScript

Simple checks read the page with scripts turned off, which is faster and safer. If your page builds its content with JavaScript, that content isn't there yet, so the check can't be judged.

What to do: Ask your assistant to make this check interactive ("execution": "interactive"). It will then load the page in a full browser.

More than one thing matched

The check looks for exactly one thing, like one “Buy” button, and found several. AsBuilt won't guess which one you meant.

What to do: Make the check more specific: use the exact visible words, or check the area of the page the thing lives in. Your assistant can rewrite it.

The wording didn't match exactly

AsBuilt found something close, such as text that contains your words, or a link where the check expected a button, but not an exact match. It's flagging this instead of guessing.

What to do: Look at what AsBuilt saw. If the page is right, update the check's wording or type. If the page is wrong, that's your fix.

Some of the page was blocked

For safety, AsBuilt only loads what's allowed. If parts of the page came from other sites, they were blocked, so the page might not have looked complete.

What to do: If those requests are part of your app, ask your assistant to allow browser network access for this check. That needs your approval, and it's recorded in the check file so it shows up in the pull request.

“Must not be shown” couldn't be confirmed

Checks that something is not on a page only count when AsBuilt is sure the page loaded properly. An error page also doesn't show the thing, so that can't count as a pass.

What to do: Fix whatever stopped the page loading (see the sections above), then run again.

The page or a step didn't load

AsBuilt couldn't open the page, or a click or step in the journey didn't finish. Anything after that point couldn't be checked.

What to do: Open the preview and try the same steps yourself. Check that the start path in the check exists on the preview and that the button names match what's on screen.

No screenshot

The check ran, but AsBuilt couldn't save a screenshot as evidence. Without evidence it won't mark the result as verified.

What to do: Re-run the workflow. If it keeps happening, report it.

What AsBuilt can and can't check

AsBuilt opens your preview in a real browser on desktop and mobile and checks what a person would see: text, headings, buttons, links, and what happens after clicks, typing and sign-in with a test account.

  • It can't check payments, emails or texts, or anything only your server or database knows, like whether an order was really saved.
  • It won't add to a cart, check out or take order steps unless you approve each step as a test action for a test site, and it never signs in with a real person's account.
  • It only checks what's in your checks. All passing means those checks passed, not that the whole app works. The coverage line in each comment shows which features in your feature map don't have checks yet.
  • The preview may not match the commit exactly if your host serves a cached or different build.

What to do: test payments, emails and server-side rules with your app's own tests, and use AsBuilt for what people see.

Checking cart, checkout and order steps on a test site

By default AsBuilt refuses any step that could change real data, like “Add to cart”, “Continue to payment” or “Done picking”. On a test site you can allow the ones you choose:

  • You approve each step. Your assistant lists every risky step in plain words and records only the ones you approve in the check file, so they show in the pull request.
  • The page has to prove it's a test site. The check names text that only your test site shows, like a “TEST SITE” banner. Before every step AsBuilt looks for it, and if it isn't there, nothing is clicked.
  • The workflow has to allow it. Add allow-test-actions: true to the AsBuilt step, only in a workflow that never checks your live site.

Not supported yet: typing a card inside a payment provider's secure frame, and steps that need two accounts (like a shopper paying and a store marking the order ready).

Still stuck?

Ask in GitHub Discussions, or open an issue if something looks broken. Include the check file and a link to the workflow run, and leave out passwords and private code. AsBuilt is maintained by one person; expect a reply within about a week.
